## Длительные измерения

Linux, CPU quota `/sys/fs/cgroup/cpu.max = 200000 100000` (2 ядра), ONNX CPU,
2 inference threads, 2 decoder threads, FFmpeg transcode — 1 thread.
Прогрев 5 с, затем фактическое окно около 60 с, источники — файлы с backpressure.
В этих замерах PPE отключён, running включён с прежними порогами.
**analytics здесь означает motion analytics, а не TPU-полный кадр.**

Не следует сравнивать эти E2E числа с worker inference из старого hardware report.

Одиночный прогон: всего 310 кадров; история Running готова на 282 кадрах,
Radar — на 294; одновременно видны максимум 2 человека; выдано 6 ID.
Пять отдельных эпизодов входа: треки 1, 2, 3, 4, 5, время источника
6.6066, 27.8111, 39.2058, 40.8074, 53.2032 с. Треки 3/4 дают два независимых
инцидента, без объединения людей только по камере/зоне. Проверенной доли
ID switches по ручной разметке нет; число выданных ID ей не равно.
Положительного события бега не найдено. Это не доказывает recall детектора бега.

Два потока: 198 кадров на каждой камере за весь прогон, разные camera/session,
отдельные трекеры, по 2 инцидента в просмотренной части. CPU не успевает идти
с исходной скоростью файлов. `dropped=0` означает ограниченную очередь и
замедление файла, **не** realtime двух RTSP-камер. Намеренно пропущенные при
семплировании исходные кадры считаются отдельно `sampled_out`.
TPU/failure/stale counters отсутствуют там, где ветвь TPU вообще не запускалась;
это не измеренная безошибочность TPU.

**5 FPS не доказаны.** Не набрано 300 кадров за 60 с, нет включённого настоящего
TPU PPE в этом окне. Локальное ограничение — суммарная CPU-нагрузка person,
декодирования, JPEG и записи доказательств. Person p50/p95: 131/288 мс для одной
камеры, около 246/578 мс при двух. Размер модели 640×640 и пороги сохранены.

Baseline B: 61 кадр / 64.39 с, CPU person+CPU PPE, не LinQ. Он был запущен при
параллельной браузерной диагностике; использовать его 0.95 FPS как изолированную
оценку прироста производительности нельзя.
Сравнение capture-оптимизации на выделенных последовательных прогонах:
`b06572b` — 279/60.108 = 4.642 FPS, `caddade` — 284/60.078 = 4.727 FPS.
На двух камерах: около 2.758 → 2.956 FPS на камеру. Это одиночные прогоны,
не статистически подтверждённый эффект. В новой версии `capture_decode_ms`
измеряет grab; преобразование в BGR вынесено в `capture_retrieve_ms` и делается
только для выбранных кадров. Полные значения стадий сохранены в JSON.

Отдельная исходная диагностика Running на 20 с OpenCV vtest с настоящим person
ONNX: 1 FPS — 0/20 кадров с достаточной историей, 5 FPS — 98/100. Порог и
`min_samples=3` не снижались. Это вспомогательная проверка частоты, не промышленная
выборка и не распознавание положительного бега. Чужие непроверенные по лицензии
vtest-медиа не публикуются.
